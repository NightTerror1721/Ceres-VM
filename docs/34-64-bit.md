# 64-bit operations on register pairs

[← Back to index](README.md)

The machine stays a 32-bit one - its registers, addresses and memory accesses are 32 bits - but 44 opcodes
work on **pairs** of registers: 64-bit integers in two integer registers and IEEE 754 binary64 doubles in two float
registers (plan/v2 SPEC 6, normative). They are what `long long` and `double` compile to.

## Register pairs

| Pair | Registers | What it holds |
| --- | --- | --- |
| `x0`–`x6` | `xN` = `r(2N)`:`r(2N+1)`, so `x1` is `r2:r3` | a 64-bit integer, low word in the even register |
| `d0`–`d7` | `dN` = `f(2N)`:`f(2N+1)`, so `d1` is `f2:f3` | a binary64 double, low word in the even register |

The low word goes in the even register, as it goes first in memory: a pair and the eight bytes it was loaded
from are laid out the same way. `x7` would be `r14:r15`, the frame and stack pointers, and is not a pair: the
assembler refuses it, and the machine refuses an instruction that names it.

A pair is still its two registers. `add64 x1, x2, x3` changes `r2` and `r3`; `ldr r4, …` changes the low half of
`x2`. The float bank keeps raw bits (plan/v2 F3.2), so the two halves of a double are just two words and a NaN's
payload survives every move.

In the encoding a pair field holds its even register's number (`x3` is `6`), in the same 4-bit fields as any
register. An **odd** number there, or `14` for an integer pair, is an `IllegalInstruction` with `FaultReason`
`RegisterPair` (8). A subfield that names no instruction (below) is `BadSubfield` (10), and an opcode nobody has
is `UnknownOpcode` (9) - see [Devices and the bus](35-Devices-and-Bus.md#which-rule-a-fault-broke).

## Flags

- `add64`, `sub64`, `neg64`, `cmp64`: Zero, Sign (bit 63), Carry (unsigned carry or borrow of 64 bits), Overflow
  (signed overflow of 64 bits). After `cmp64` every comparison jump works as after `cmp`: `jls`, `jab`, `jbe`…
- `mull`, `imull`, `mul64`, `sxt64`: Zero and Sign of the 64-bit result, Carry and Overflow clear.
- `div64`, `mod64`, `imod64`: Zero and Sign. `idiv64` of `INT64_MIN` by -1 gives `INT64_MIN` and sets Overflow;
  `imod64` of the same gives 0.
- The shifts: Zero, Sign, and Carry is the last bit shifted out. A shift by 0 changes nothing, flags included.
- `clz64`, `ctz64`, `popcnt64`: what `clz` sets, from the count.
- The doubles: those of the 32-bit instruction each mirrors (`fadd.d` as `fadd`, `fcmp.d` as `fcmp`, …); `fsqrt.d`,
  `fabs.d`, the roundings, `fcopysign.d`, `fclass.d`, `fcvt` and the moves set none.
- Loads, stores and `mov64` set none.

A division by zero - `div64`, `idiv64`, `mod64`, `imod64`, and `fdiv.d`/`fmod.d` unless `FeatureIeeeDivide` is on -
does what `div` does: the Trap flag, or the `DivisionByZero` interrupt when division faults are enabled, and the
destination is left alone.

## Integer instructions

| Opcode | Syntax | Operation | Cycles |
| --- | --- | --- | --- |
| `0xD7` | `add64 xd, xs, xt` | `xd = xs + xt` | 2 |
| `0xD8` | `sub64 xd, xs, xt` | `xd = xs - xt` | 2 |
| `0xD9` | `neg64 xd, xs` | `xd = -xs` | 2 |
| `0xDA` | `cmp64 xs, xt` | the flags of `xs - xt` | 2 |
| `0xDB` | `mull xd, rs, rt` | `xd = (u64)rs * (u64)rt` | 4 |
| `0xDC` | `imull xd, rs, rt` | `xd = (i64)rs * (i64)rt` | 4 |
| `0xDD` | `mul64 xd, xs, xt` | the low 64 bits of `xs * xt` | 6 |
| `0xDE` / `0xDF` | `div64` / `idiv64 xd, xs, xt` | quotient, unsigned / signed | 40 |
| `0xE0` / `0xE1` | `mod64` / `imod64 xd, xs, xt` | remainder, unsigned / signed | 40 |
| `0xE2`–`0xE4` | `shl64` / `shr64` / `sar64 xd, xs, rt` | shift by `rt & 63` | 2 |
| `0xE5` | `shl64` / `shr64` / `sar64 xd, xs, 0..63` | shift by an immediate | 2 |
| `0xE6` | `sxt64 xd, rs` | `xd = (i64)(i32)rs` | 1 |
| `0xE7` | `clz64` / `ctz64` / `popcnt64 rd, xs` | a count into a 32-bit register (64 for 0) | 2 |
| `0xE8` | `mov64 xd, xs` | copy | 1 |
| `0xE9` / `0xEB` | `ldrd xd, [rs + imm]` / `[rs + rt]` | 64-bit load | 3 |
| `0xEA` / `0xEC` | `strd [rd + imm], xs` / `[rd + rt], xs` | 64-bit store | 3 |
| `0xED` | `ldrd xd, [pc + imm]` | PC-relative load (what `li64` becomes) | 3 |

## Double instructions

| Opcode | Syntax | Operation | Cycles |
| --- | --- | --- | --- |
| `0xEF`–`0xF1` | `fadd.d` / `fsub.d` / `fmul.d dd, ds, dt` | IEEE binary64 | 4 / 4 / 5 |
| `0xF2` | `fdiv.d dd, ds, dt` | division | 20 |
| `0xF3` | `fma.d dd, ds, dt` | `dd = dd + ds * dt`, **one** rounding | 6 |
| `0xF4` | `fsqrt.d dd, ds` | square root | 24 |
| `0xF5` | `fcmp.d ds, dt` | the flags `fcmp` sets | 3 |
| `0xF6` | `fmin.d` / `fmax.d dd, ds, dt` | | 3 |
| `0xF7` | `fmod.d dd, ds, dt` | remainder, as `fmod` | 30 |
| `0xF8` | `fneg.d` / `fabs.d` / `fround.d` / `ffloor.d` / `fceil.d` / `ftrunc.d dd, ds` | `fround.d` rounds ties to even | 3 |
| `0xF9` | `fcopysign.d dd, ds, dt` | the magnitude of `ds`, the sign of `dt` | 2 |
| `0xFA` | `fclass.d rd, ds` | the mask `fclass` gives | 2 |
| `0xFB` | `fcvt.<to>.<from>` | a conversion, below | 3, 4 with a 64-bit integer |
| `0xFC` | `fmov.d dd, ds` | copy | 1 |
| `0xFD` / `0x7A` / `0x7C` | `fldr.d dd, [rs + imm]` / `[rs + rt]` / `[pc + imm]` | 64-bit load | 3 |
| `0xFE` / `0x7B` | `fstr.d [rd + imm], ds` / `[rd + rt], ds` | 64-bit store | 3 |
| `0x7D` | `mtf.d dd, xs` | the bits of an integer pair into a double pair | 1 |
| `0x7E` | `mff.d xd, ds` | the other way | 1 |

The arithmetic is the host's `double`, rounded to nearest even, and gives what IEEE 754 binary64 does bit for bit:
the machine's tests run the STDLIB's 4000 vectors (`tests/data/f64_vectors.inc`) through it and every result
matches, subnormals and NaNs included. A NaN made from nothing (`sqrt(-1)`, `0/0`) is the x86-64 default NaN,
`0xFFF8000000000000`, on the development host.

### `fcvt`

`w` is a 32-bit signed integer, `wu` unsigned, `l` a signed integer pair, `lu` unsigned, `s` a float, `d` a double
pair; the destination comes first. The kind is in bits 3:0; 14 and 15 are `BadSubfield`.

| Kind | Mnemonic | | Kind | Mnemonic | |
| --- | --- | --- | --- | --- | --- |
| 0 | `fcvt.d.s dd, fs` | | 7 | `fcvt.d.lu dd, xs` | |
| 1 | `fcvt.s.d fd, ds` | | 8 | `fcvt.l.d xd, ds` | |
| 2 | `fcvt.d.w dd, rs` | | 9 | `fcvt.lu.d xd, ds` | |
| 3 | `fcvt.d.wu dd, rs` | | 10 | `fcvt.s.l fd, xs` | |
| 4 | `fcvt.w.d rd, ds` | | 11 | `fcvt.s.lu fd, xs` | |
| 5 | `fcvt.wu.d rd, ds` | | 12 | `fcvt.l.s xd, fs` | |
| 6 | `fcvt.d.l dd, xs` | | 13 | `fcvt.lu.s xd, fs` | |

To a float or a double: rounded to nearest even. To an integer: truncated toward zero and **saturated** at the ends
of the range, with NaN as 0 (so `fcvt.wu.d` of -3.0 is 0 and of 1e20 is `0xFFFFFFFF`). `ftoi`/`ftoii` keep their
own behaviour: they do not saturate.

## Loads and stores

`ldrd`, `strd`, `fldr.d` and `fstr.d` move eight bytes aligned to **4**; anywhere else is an `AlignmentFault`
whose `FaultAccess` says 8 bytes. The low word comes first. To memory the two words are one access, and cost the
3 cycles of the table; to a device they are **two** 32-bit accesses, low then high, each paying 4 (9 cycles in all).
That order is what lets `ldrd` read a latched pair of registers - the timer's `CyclesLow`/`CyclesHigh`, its
`NanosLow`/`NanosHigh` - as one instant: the low read latches the high word.

A load writes the pair only once both words are in. A store that faults on its second word has written the first;
the handler's `iret` runs the whole store again.

## In the assembler

- The pairs are written `x0`–`x6` and `d0`–`d7`, in either case, and an `alias` can name one.
- A mnemonic with dots is read whole when it is written without spaces: `fadd.d`, `fcvt.l.d`.
- An operand of the wrong bank is reported as such: `'ADD64' takes an integer pair (x0-x6) as operand 2, not an
  integer register (r0-r15)`.
- Data can be `u64`, `i64` or `f64`: eight bytes, aligned to 4. An integer literal may need more than 32 bits, and a
  float literal is read in double precision; an initializer of a 64-bit type is worked out in 64 bits. See
  [Data types and literals](11-Data-Types-and-Literals.md#64-bit-types).
- `li64 xd, <constant>` puts a 64-bit constant in a pair, from the literal pool; so does `ldv dd, <constant>` for
  a double. `ldv`/`stv`, `ldrd xd, [var]`, `strd [var], xs`, `fldr.d dd, [var]` and `fstr.d [var], ds` reach a
  64-bit variable. The loads are three words that the linker relaxes to one PC-relative word when the variable
  is within reach; the stores stay three. See [Pseudo-instructions](06-Pseudo-Instructions.md#li64-and-64-bit-variables).

```casm
@data
    let total: i64 = 0
    let scale: f64 = 0.001
@text
global main:
    li64 x1, 5000000000         // more than 32 bits
    ldv x2, total
    add64 x2, x2, x1
    stv total, x2

    fcvt.d.l d1, x2             // to a double
    ldv d2, scale
    fmul.d d1, d1, d2           // 5000000.0
    halt
```

## In the debugger

`regs` prints `x0`–`x6` as 64-bit numbers when a high word is in use, and `d0`–`d7` beside the float bank; an
expression can name `x1` (read as an unsigned 64-bit integer) or `d2` (a double), and a load can be typed `u64`,
`i64` or `f64`: `f64[r1]`. See [The debugger](22-Debugger.md#register-pairs).
